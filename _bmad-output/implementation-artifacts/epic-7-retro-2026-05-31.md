## What Went Well

### JSON-RPC Stayed an Adapter

The most important Epic 7 outcome is that RPC remained a bridge over shared runtime contracts:

- `packages/rpc` owns protocol parsing, request routing, response/error shapes, stdout-safe serving, and bounded serialization.
- `packages/core` remains the owner of task lifecycle, sessions, approvals, final summaries, learning reviews, event history, and provider configuration.
- `packages/cli` wires the RPC server into the existing runtime rather than creating a separate agent loop.

This preserved the Epic 6 guardrail: adapters can expose and steer runtime behavior, but they must not become independent sources of runtime truth.

### Stdout Purity Became a First-Class Test Contract

Story 7.1 established that JSON-RPC stdout must be line-delimited protocol output only. Later stories kept adding subprocess tests that parse stdout as JSON-RPC messages and assert `jsonrpc: "2.0"`.

This was especially valuable because RPC clients are brittle by design: one accidental log line can corrupt an integration. The test suite now treats stdout purity as behavior, not convention.

### Review Findings Became Focused Regression Tests

Epic 7 repeated the strongest pattern from Epics 5 and 6: review issues were turned into tests before fixes were accepted.

Examples:

- Story 7.5 review hardened approval response validation, bounds, and environment exposure handling.
- Story 7.6 review hardened terminal task gating, taskId validation, session filtering, reuse evidence, null safety, and error mapping.
- Story 7.7 review added regressions for created-session state with no active task, accepted task scope visibility, unknown-param rejection, no-session diagnostic metadata, and CLI capability/stdout behavior.

The result is a stronger RPC contract than the initial happy-path implementation would have produced.

### Scope and Redaction Boundaries Were Reused Across Methods

The same safety pattern now appears across RPC methods:

- Require scoped `cwd`.
- Reject out-of-scope cwd with structured `INVALID_CWD` errors.
- Reject malformed params with safe `INVALID_PARAMS` errors.
- Keep provider output to provider name/model only.
- Omit secrets, private local paths, raw stdout/stderr, patch bodies, env values, and unauthorized memory/session data.
- Cap arrays/counts so responses cannot become unbounded dumps.

That consistency will make future docs and external clients easier to maintain.

### GitNexus Impact Discipline Reduced Core Runtime Risk

Several potential changes touched broad runtime/class surfaces. The Story 7.7 review fix is the clearest example: `AgentRuntime` had a HIGH class-level blast radius, so the implementation stayed in the RPC bridge sidecar instead of modifying core runtime state.

This produced a narrower, reversible patch while still satisfying the story contract.

## Challenges and Growth Areas

### Adapter State Alignment Is Still Subtle

RPC has to reconcile several runtime views:

- created/resumed session state,
- active task state,
- accepted task scopes,
- event history,
- pending approvals,
- final summaries,
- learning review artifacts,
- protocol metadata.

Story 7.7 exposed a gap: a created RPC session with no active task still needed visible session state. The fix was intentionally kept in the bridge layer, but the lesson is broader: adapter-visible state needs explicit coverage for idle, active, terminal, and no-session states.

### No-Session Semantics Need Careful Product Decisions

Story 7.7 originally described a structured `NO_ACTIVE_SESSION` error path, while the implemented and reviewed behavior preserved a successful state payload with diagnostic metadata. That decision is reasonable for status-display clients, but future protocol docs should describe it explicitly so clients do not guess whether no-session is exceptional or informational.

### Parameter Validation Is Easy to Under-Specify

Unknown param rejection arrived as a review gap. RPC methods should define allowed param keys up front and test extra-field rejection, not only malformed-type rejection.

This is especially important before Epic 8, where auth/config methods may receive provider names, auth modes, credential references, browser/device flow fields, and config scopes.

### Existing Workspace Hygiene Can Obscure Story Diffs

During Epic 7 closeout, unrelated `.codex/` and `_bmad/` workspace changes remained present. Story-scoped staging and checks prevented those files from entering commits, but the noise made every status check harder to read.

Future story starts should either stash, commit separately, or explicitly inventory unrelated workspace changes before edits begin.

### GitNexus Detect-Changes Parity Still Needs Fallback Handling

AGENTS.md still refers to `gitnexus_detect_changes()`, but the local CLI surface exposes `analyze`, `status`, `query`, `context`, and `impact`, not a CLI `detect-changes` command. The working fallback remains:

- inspect `git diff` and staged scope,
- run targeted `gitnexus impact`,
- run `npx gitnexus analyze`,
- verify `npx gitnexus status`.

### `npm run lint` Still Mirrors Typecheck

The unresolved quality item from prior retrospectives remains: `npm run lint` is still a typecheck alias. Typechecking is useful, but it is not an independent style/static-quality gate.

## Key Lessons

1. JSON-RPC stdout purity must be tested through subprocess parsing, not trusted by convention.
2. RPC methods should validate exact allowed params, including unknown-field rejection.
3. External-client APIs need explicit idle-state and no-session semantics.
4. Adapter sidecars can be safer than core runtime changes when the core symbol has high blast radius.
5. Bounded protocol responses are easier to reason about when every method follows the same redaction and array-cap rules.
6. Review findings should become regressions before implementation patches are accepted.
7. RPC should expose runtime truth; it should not create a second source of truth.
8. Story-scoped checks are necessary when unrelated workspace changes are present, but a cleaner workspace is better before starting a new epic.

## Risks Entering Epic 8

### Auth Must Not Leak Secrets

Provider login/logout/refresh and effective configuration surfaces will handle the most sensitive data in the product. Tests must include secret-like values, private paths, tokens, API keys, refresh tokens, and auth-file paths.

### Auth Flow Belongs Behind Provider Modules

Story 8.1 requires OAuth behavior to stay behind provider auth modules, not inside the agent loop. This mirrors the Epic 7 adapter lesson: keep boundaries explicit and avoid spreading provider-specific logic through runtime control flow.

### Non-OAuth Providers Need Good Failure UX

Many providers will not support interactive login. The unsupported-login path should return a structured explanation and next action, not a stack trace or generic failure.

### Credential File Permissions Are Cross-Platform

Story 8.3 will need careful local-permission handling, especially across macOS/Linux and potential Windows behavior. Tests should isolate filesystem permissions and avoid writing real user credentials.

### Effective Configuration Must Be Useful but Redacted

Story 8.6 should expose enough merged config/auth state to debug provider setup while still redacting secret values, local private paths, and credential material.
